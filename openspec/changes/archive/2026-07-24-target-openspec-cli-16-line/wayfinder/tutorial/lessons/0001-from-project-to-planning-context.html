OpenSpec 不是在发明 package monorepo

1.5 的核心变化是把“命令在哪个规划根执行”和“规划时可以读取哪些外部规范”变成显式模型。 它处理的是 planning topology，不是 npm/pnpm package graph。

先掌握三个共享实体

Project root 代码仓库自己的 openspec/。代码和规划一起版本化。
Store 独立 Git 仓库中的 openspec/。规划可以先于代码，或跨多个代码仓库。
Reference 当前根对另一个 Store 的只读声明。只增加可读取的规范，不改变写入目标。
一个命令始终只选择一个可写 OpenSpec root。Reference 可以有多个，但都是只读上下文。

1.6 限制：Reference 的目标必须是本机注册的 Store id，不能直接填写任意 package 路径或未注册的项目规划根。store setup 面向新建独立规划仓库，会拒绝在已有 Git 仓库内部创建；但 store register 可以为一个已有的健康规划根补充 Store 身份并注册，包括 monorepo 内没有独立 .git 的 package root。

再区分两个本机视图

Context 从当前 root 和它声明的 References 实时推导出来的工作上下文。
Workset 用户手工保存的一组本地目录，用来一次打开多个仓库；不表达规划依赖。
Store registry 用户/机器级把 Store id 映射到 checkout 路径，默认跨项目共享。不会提交，也不会自动 clone/pull/push。

references: 只声明 Store id，不会自动注册。官方用户入口是 store setup 和 store register；它们负责健康检查、身份校验、路径规范化、冲突检测和加锁写入。 可以用 XDG_DATA_HOME 为一组进程隔离 registry，但这不是项目配置，也不会随仓库自动生效。

它和 monorepo 的真正关系

问题 package monorepo OpenSpec 1.5/1.6
一等实体 package、依赖边、workspace OpenSpec root、Store、Reference
主要动作 安装、构建、测试、发布 选择规划根、生成 artifact、校验、归档
跨仓库 通常不处理 Store 和 Reference 正面处理
写入模型 可同时操作多个 package 每个命令只写一个解析后的 root

一个跨团队例子

platform-reqs (Store, platform team owns it)
  openspec/specs/auth/spec.md
            |
            | Reference: read-only
            v
api-server (Project root) ---- current writable change
            ^
            | same external requirements
web-app (Project root) ------- its own writable change

workset "auth" = [platform-reqs, api-server, web-app]
                   only a personal open-these-folders view

这里没有“一个 change 同时修改三个 root”的机制。通常是平台规范作为 Reference，两个代码仓库各自维护自己的 change。Store 也可以反过来成为唯一规划根，让多个代码仓库都通过 store: 指针使用同一套 change。

因此，在 monorepo 内给每个 package 建立独立 openspec/ 可以获得最近根隔离。它们最初不能直接通过 references: 互相引用；但已有健康 root 可以通过 store register --yes 获得 Store 身份，随后按 Store id 被其它 package 引用。

对 OpenSpecUI 的三个产品层级

层级 用户体验 是否是 1.6 正确性的前提
L0 Root-correct 从任意项目启动，UI 展示 CLI 实际选中的一个 root；读写、监听、归档都不走错目录。 是
L1 Context-aware 展示 References、健康状态和外部 spec 索引，解释当前 change 借用了哪些上游规范。 对完整 Stores 体验重要，但可单独分期
L2 Workspace orchestration Store CRUD、注册修复、Context 浏览、Workset 创建和多仓库导航。 否，是更高阶产品能力

检验理解

在 api-server 中声明 references: [platform-reqs] 后运行 openspec new change fix-auth，change 应写到哪里？

答案：写到 api-server 自己的 root。Reference 只增加只读上下文，不重定向写入。
